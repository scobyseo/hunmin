# hunmin 0.2.0 — GitHub Release notes (in progress)

## What 0.2 ships

0.2 is the Windows IME release (TSF frontend, issue #64 milestone A). Per the
release plan in `docs/MILESTONES.md` §0.2 it is a frontend-only lane: no engine
change is planned, and the commit-only preedit buffer adapter in
`frontends/tsf/src/tsf.cpp` needed no libhunmin change.

Done (measured on this host, Windows 11 + VS2022 BuildTools 14.44 +
Windows SDK 10.0.26100):

- `frontends/tsf/src/tsf.cpp` — the TIP: COM class factory, `DllRegisterServer`,
  key-down sink (`OnTestKeyDown`/`OnKeyDown`), commit-only overlay presentation,
  deactivation flush.
- `hunmin-tsf.dll` builds natively via MSVC (`frontends/tsf/build-msvc/`).
- Registration verified end-to-end in Notepad: `regsvr32` writes the CLSID,
  language profile (`0x0412` Korean), `Enable = 0x1`, and the SortOrder slot;
  `GetActiveProfile` reports the Hunmin CLSID; selection via Win+Space loads the
  TIP and keys compose.
- `docs/WINDOWS-TSF-REGISTRATION.md` and `docs/WINDOWS-TSF-BUFFERING.md` — the
  registration / key-down chain and the commit-only buffering contract.
- `docs/ENVIRONMENT.md` "Windows 0.2 development environment" — the host
  toolchain and build commands.

Open (issue #65, milestone B — core input integration):

- The key-down → engine → overlay end-to-end chain is documented; the remaining
  #65 work is integrating it into a shippable TIP and closing the open questions
  in `docs/WINDOWS-TSF-BUFFERING.md` (UWP/console overlay need, candidate window
  behaviour, caret-rect source).
- `DllUnregisterServer` deletes only `HKCR\CLSID\{CLSID}`; the HKLM TIP tree and
  per-user profile entries remain (recorded finding, not fixed).
- No TAT measurement; registration/activation remains device-bound.
- No CI TIP lane — the `windows` job stays `if: false` per issue #51.

## Milestone C (issue #66, layout wiring + data loading)

Measured 2026-10-17 on this host (`docs/WINDOWS-TSF-CONFIG.md`):

- The layout pair comes from a configuration store, not hard-coded ids:
  `HKCU\Software\Hunmin\TSF` (`HangulLayout` / `LatinLayout`), env override
  (`HUNMIN_TSF_HANGUL_LAYOUT` / `HUNMIN_TSF_LATIN_LAYOUT`), fcitx5-mirrored
  defaults (`sin3-p2` / `us-qwerty`). Slots are validated against the loaded
  data (supported + mode match), and the Hangul/English toggle switches the
  configured pair. The settings dialog that writes the store is #71.
- The build stages `libhunmin/data` beside `hunmin-tsf.dll` (and the tier-F1
  harnesses), so the shipped `<module>\data` branch holds real data.
- The data search collapsed to first-present priority, after measuring that
  the additive chain loaded one staged tree twice (15 files →
  `hunmin_ctx_layout_count()` 30).
- Tier F1 grew `tsf-config-test`, `tsf-datadir-test` and a dubeolsik win32
  trace; the trace runner pins layouts from trace meta instead of host
  settings. Measured registration drift fixed the same day: the standalone
  `frontends/tsf` configure had registered ZERO tier-F1 tests (no
  `enable_testing()`; the `Python3_FOUND` guard broke under an explicit
  `-DPython3_EXECUTABLE`).

## Milestone D (issue #67, candidate & edit-mode UX)

Measured 2026-10-17 on this host (`docs/WINDOWS-TSF-CANDIDATES.md`):

- The Hanja candidate window over the WHOLE buffered word — type a Hangul
  word, press the Hanja key, pick from the dictionary (krdict words, idioms,
  hanja).
  `안녕` → 2 candidates, `가` → 65, `중국` → 1 (`중국` was the motivating
  case: well-known hanja terms out of the dictionary instead of one
  character at a time). No engine change: `hunmin_suggest_*` already
  keyed the tables by words.
- fcitx5 keyboard semantics (digits/arrows/page/Return/Esc, close-and-
  continue on any other key), the ruled 10-per-page cap of issue #45, and
  commit-replaces-composition with no surrounding-text use.
- Tier F1 gained `tsf-candidate-test` (13 cases: open/commit/motion/paging/
  zero-candidate pass-through/dead-digit fall-through/toggle-and-Esc close/
  the backspace edit walk); the mock-TSF trace harness stays green over the
  modified adapter (`frontends/tsf/build-msvc`, 7/7 including the three
  win32 conformance traces).

## Version-string convention (ruled 2026-10-12, issue #9)

The release is `0.2.0` everywhere: `CMakeLists.txt`, `debian/changelog`, and the
git tag. No tag `0.2.0` exists yet; `tools/release-0.1.sh` (used for 0.1) is the
template for the 0.2 release run, parameterised by `$TAG`.

## How a user gets 0.2

```sh
# Windows TSF TIP (built locally from a clean checkout)
cmake -S . -B build-msvc -G "Visual Studio 17 2022" -A x64
cmake --build build-msvc --target hunmin   # core: hunmin.lib
cmake -S frontends/tsf -B frontends/tsf/build-msvc -G "Visual Studio 17 2022" -A x64 \
  -DHUNMIN_LIB=.../build-msvc/Release/hunmin.lib
cmake --build frontends/tsf/build-msvc --target hunmin-tsf
# then register: frontends/tsf/register-tsf.bat (elevation required)
```

No `.deb` for 0.2 — the `.deb` channel is 0.1's; 0.2's artefact is
`hunmin-tsf.dll` plus registration instructions. A user needs repo access to
fetch anything (repository is **private until after 0.2**, ruling 2026-10-16).
