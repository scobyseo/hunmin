# hunmin 0.2.0 — GitHub Release notes

Status quo refreshed 2026-10-19 (issue #99's PR #117); each section keeps the
date its figures were measured. The release run itself is recorded at the end
("0.2.0 release run (2026-10-29)").

## What 0.2 ships

0.2 is the Windows IME release (the TSF frontend, issue #64 milestone A), and
it ships on THREE channels:

- **Windows** — the installation package (`hunmin-0.2.0-setup.exe`, issue
  #99): the TIP DLL with the engine static-linked inside, the Korean data
  tables staged beneath it, the self-contained settings exe, and the
  installer running registration and its mirror (issue #84).
- **Linux** — the `.deb` (the 0.1 channel ships on): maintainer ruling
  2026-10-19, verbatim: "there will be .deb in 0.2 because the behavior of
  fcitx5 changes according to tsf implementation". Measured basis below.
- **Android** — the release APK: maintainer ruling 2026-10-19, verbatim:
  "actually, android apk should be released too." 0.1 published NO APK
  asset (debug `assembleDebug` only, built locally); 0.2 is the first
  release that ships one. Measured basis: `git diff --stat 0.1.0..HEAD --
  frontends/android` is 655 insertions, 488 deletions over 24 files — the
  word-boundary preedit buffer adapter (#75), the `hunmin_ic_process_key`
  migration (#105), the measured R8 shrinker path — so the released APK is
  not the 0.1 build either.

The engine is not the 0.1 engine. `git diff --stat 0.1.0..HEAD --
libhunmin/src frontends/fcitx5 debian` is 634 insertions, 227 deletions over
14 files, and `libhunmin/include/hunmin.h` grew +39/−4: the explicit-modifier
key entry point (#90), the `hunmin_ic_process_key` migration (#106), the
case-encoding `ch` input ruling (#87) — and the fcitx5 addon's behavior
moves with the TSF implementation's, which is the .deb ruling above.

Done (measured on this host, Windows 11 + VS2022 BuildTools 14.44 +
Windows SDK 10.0.26100):

- `frontends/tsf/src/tsf.cpp` — the TIP: COM class factory,
  `DllRegisterServer`, key-down sink (`OnTestKeyDown`/`OnKeyDown`),
  deactivation flush; **native composition preedit** (issue #98, PR #114)
  replaced the milestone-B commit-only overlay window; the F9 Hanja
  candidate window over the whole buffered word (milestone D, issue #67);
  edit/navigation keys as boundary + passthrough (issue #95); the CTRL/ALT
  chord in hangul mode ruled transient, no language toggle (issue #101); the
  VK→base half migrated to `hunmin_ic_process_key` (issue #106); the Hanja
  fallback fix — zero-whole-word lookups produce candidates from the last
  syllable (PR #111).
- Layout wiring + data loading (milestone C, issue #66): the layout pair
  from a configuration store, `libhunmin/data` staged beside the DLL.
- The settings surface (issue #71): the WinUI 3 settings exe
  (`hunmin-tsf-settingsui`, self-contained), the interim dialog reachable
  as the rundll32 fallback.
- Registration mirror (issue #84): `DllUnregisterServer` removes the full
  registered state — the CLSID tree, the HKLM CTF TIP tree, the two
  categories, the language profile.
- The installation package (issue #99, PR #117): `hunmin.iss` +
  `tools/build-windows-installer.sh` + the package contract in
  `docs/WINDOWS-INSTALLER.md` (the `/MT` TIP — no VC redist on a clean
  image; the installer runs `regsvr32` on the installed DLL and mirrors it
  on uninstall).
- `hunmin-tsf.dll` builds natively via MSVC (`frontends/tsf/build-msvc/`);
  the tier-F1 mock-TSF harness (issue #80) makes the frontend testable
  without a live TIP.
- Registration verified end-to-end in Notepad: `regsvr32` writes the CLSID,
  language profile (`0x0412` Korean), `Enable = 0x1`, and the SortOrder slot;
  `GetActiveProfile` reports the Hunmin CLSID; selection via Win+Space loads
  the TIP and keys compose.
- `docs/WINDOWS-TSF-REGISTRATION.md`, `docs/WINDOWS-TSF-BUFFERING.md`,
  `docs/WINDOWS-TSF-CONFIG.md`, `docs/WINDOWS-TSF-CANDIDATES.md`,
  `docs/WINDOWS-INSTALLER.md`, and `docs/ENVIRONMENT.md` "Windows 0.2
  development environment".

## Milestone C (issue #66, layout wiring + data loading)

Measured 2026-10-17 on this host (`docs/WINDOWS-TSF-CONFIG.md`):

- The layout pair comes from a configuration store, not hard-coded ids:
  `HKCU\Software\Hunmin\TSF` (`HangulLayout` / `LatinLayout`), env override
  (`HUNMIN_TSF_HANGUL_LAYOUT` / `HUNMIN_TSF_LATIN_LAYOUT`), fcitx5-mirrored
  defaults (`sin3-p2` / `us-qwerty`). Slots are validated against the loaded
  data (supported + mode match), and the Hangul/English toggle switches the
  configured pair. The settings dialog that writes the store is #71.
- The build stages `libhunmin/data` beside `hunmin-tsf.dll` (and the tier-F1
  harnesses), so the shipped `<module>\data` branch holds real data.
- The data search collapsed to first-present priority, after measuring that
  the additive chain loaded one staged tree twice (15 files →
  `hunmin_ctx_layout_count()` 30).
- Tier F1 grew `tsf-config-test`, `tsf-datadir-test` and a dubeolsik win32
  trace; the trace runner pins layouts from trace meta instead of host
  settings. Measured registration drift fixed the same day: the standalone
  `frontends/tsf` configure had registered ZERO tier-F1 tests (no
  `enable_testing()`; the `Python3_FOUND` guard broke under an explicit
  `-DPython3_EXECUTABLE`).

## How a user gets 0.2

**The release shape (issue #99):** the 0.2 installation package —
`hunmin-0.2.0-setup.exe`, built by `tools/build-windows-installer.sh` from
`frontends/tsf/installer/hunmin.iss`. Double-click, accept elevation, done:
it stages the TIP DLL (engine static-linked inside, CRT statically linked so
a clean Windows image needs no VC redist), the Korean data tables beneath it
(`<install>\data\`), the self-contained settings exe, the Start-menu entry
(`Hunmin IME 설정`), registers through the DLL's own `DllRegisterServer`
(regsvr32), and its uninstall mirrors registration (issue #84's
`DllUnregisterServer`). Package shape and measured sizes:
`docs/WINDOWS-INSTALLER.md`.

**The dev-period staging** (register a build tree by hand) stays available
for development:

```sh
# Windows TSF TIP (built locally from a clean checkout)
cmake -S . -B build-msvc -G "Visual Studio 17 2022" -A x64
cmake --build build-msvc --target hunmin   # core: hunmin.lib
cmake -S frontends/tsf -B frontends/tsf/build-msvc -G "Visual Studio 17 2022" -A x64 \
  -DHUNMIN_LIB=.../build-msvc/Release/hunmin.lib
cmake --build frontends/tsf/build-msvc --target hunmin-tsf
# then register: frontends/tsf/register-tsf.bat (elevation required)
```

**The Android release APK** — maintainer ruling 2026-10-19, verbatim:
"actually, android apk should be released too." The shape that exists
(measured 2026-10-13 for issue #8, standing):

```sh
tools/build-release.sh apk              # release APK, both ABIs (arm64-v8a, x86_64)
tools/build-release.sh apk x86_64       # one ABI at a time; the app builds ALL ABIs
```

or the CI job `android-release` (`assembleRelease`, both ABIs, artefact
upload, gated on `vars.HUNMIN_BUILD_RELEASE == 'true'`). An IME is a user
app: sideload the APK, enable Hunmin in system settings, pick it as the
input method. **The signature is a generated throwaway key, not a release
key** — the 0.1 stance stands: the APK installs and runs and `apksigner
verify` is the check, and the keystore PATH contradiction is closed (issue
#1, `local.properties`), but a ship-grade release key is still the
maintainer's later decision. The release build is never typed into: no CI
job and no scripted round installs the release APK — `tools/android-e2e.sh`
drives the debug APK by design (the measured standing row, REMAINING-WORK
§3).

The .deb ships in 0.2 as well — maintainer ruling 2026-10-19, verbatim:
"there will be .deb in 0.2 because the behavior of fcitx5 changes according
to tsf implementation". The measured basis: `git diff --stat 0.1.0..HEAD --
libhunmin/src frontends/fcitx5 debian` is 634 insertions, 227 deletions
over 14 files, and `libhunmin/include/hunmin.h` grew +39/−4 — the engine
under the fcitx5 addon is not the 0.1 one, so the Linux channel ships the
changed addon, not the 0.1 one. A user needs repo access to fetch either
channel (repository is **private until after 0.2**, ruling 2026-10-16).
