# MODES-POSTMORTEM — Failure of the Hangul-English Guessing Investigation

Requirements: `docs/SPEC-MODES.md`. This document holds **the failures I caused**
while investigating those requirements. Not a requirements document, but a record
left behind so that the next attempt does not repeat the same mistakes.

Status: **Complete.** New entries are added following the rules in §4.

Each entry is kept **because the wrong number looked plausible.**

# 1. What I got wrong by measuring

1. **A pass verdict that could not fail.** The first verdict for invariant I11
   assumed that as long as two identifiers appear somewhere in the file pair,
   that was enough. Because the two strings match elsewhere, it **passed against an empty `setLayouts` body.** I found it by planting a mutation.
2. **Circular measurement.** I typed Hangul words in dubeolsik and got 300/300
   correct — because the keystrokes were **generated by inverting the layout's own
   key table**, so it could not fail. It only proves the harness ran.
3. **An inverted classifier.** The josa (조사, postposition particle) / eomi
   (어미, ending) fragment test asked "does the run **end in** a josa", so every
   word ending in 다/ㅁ/ㄴ was stripped and the answer became 97.1% of words —
   meaningless. Worse, The National Institute of Korean Language lists `다` and `은` in **both in the josa list and in the eomi list**, so they cannot be split by list alone without an arbitrary priority rule.
4. **Four mutually impossible COST figures** — 55%, 60.8%, 96.0%, 29.3%. The
   corpus was made by hand and its word pool (filtered `2<=len<=4`)
   **disagreed with the filter under test (`len>=3`).** Each one was
    ** measured against a corpus that cannot exhibit the effect being measured. The 96.0% I believed longest was the most invalid.**
5. **I got the other side of the comparison right.** The verdict rule compared
   the English list against **Hangul output** (`뇬ㅅ` cannot match `system` as a
   prefix), so every case became `english=0` and the rule was recorded as 0%,
   while in reality it was working at 88.6%. **The English side must be verified with the keys the user types.**
6. **A script with no entry point.** `hermes-verify-sin3.py` ended without a
   `main()` call, printed nothing, and exited with `rc=0`. I accepted the empty
   output as a pass. **Python's rc=0 means the script ran, not that it did
   nothing. Read the script to the end before you trust the output.**
7. **I made claims about kime without measuring.** "kime passes Latin through to
   the OS" was right, but I slid from "kime has a romaja layout" all the way
   to a judgement about romaja IM registration, and I repeatedly quoted
   "kime's choice" even though kime has no dictionary at all. It is now stated in §2 and measured.
8. **I wrote it as if the user had said it, after I made up the requirement.**
   I wrote "Romaja is the English input mode" into PLAN.md as though it were
   established, without stating that it was my own inference. The user
   rejected it: that clause had been about designing IM registration by
   keyboard family from the start. **Do not write requirements into the document, as requirements, that the user did not say.**
9. **I assumed other code was broken without evidence that it differed.** From a
   single ctypes run I reported "the receive path is broken", and **I never
   compared both paths with the same keys.** When I did, `hunmin-sim --keys 'tkfka '` → gave a human, but ctypes gave
   `람` — **the CLI was right.** Part
   of that difference was mine: because `hunmin_ic_commit` is a destructive
   read, I had been consuming intermediate commits once per key. **Claiming
   a defect in someone else's code without a differential test is the same error as asserting a figure without measuring it.**
10. **Two harnesses quietly measured nothing.** `len(obj) > 40` in
    `count-corpus.py` discarded every short JSON body and tallied all JSON
    records as 0 (the first real run passed only because the corpus bodies
    were long), and the second quiet 0 in the same file was dropping whole
    records with no `data` key (`obj.get("data", [])`). `metric-2-3.py` fed
    Hangul syllables to `hunmin-sim --keys`, but that command takes
    **keyboard keys** and returns an empty commit without error. All three
    produced **plausibly small numbers** and never failed at all. **A harness
    that cannot fail must be shown capable of failing before you believe its
    output** — that is what the verification scripts under /tmp did, and all three were found there.
11. **I chased a bug that did not exist.** I burned several turns chasing the
    ghost of a Gradle parse failure on a byte-clean ASCII file. Check whether
    the artifact on disk is really broken first, not the tool.
12. **I claimed a capability that does not exist.** I put forward "let's add an
    API to libhunmin so the harness can inject synthetic text" as if there
    were viable options, but `hunmin-sim --help` shows only `--keys` and
    `--check`, and `hunmin_ic_commit_text()` does not simulate composition —
    it commits finished text. I proposed it before checking.
13. **I re-derived eleven times something the engine already knew.** The
    keystroke inversion (`measure.py`) failed 11 times over. Each round was
    guess → run → fix → run, and only on the eleventh did I begin to
    **observe** — brute-forcing the engine to get ground truth. What it
    showed was that a complex final consonant is **pressing the consonant key
    twice** (사+tt → 삿) and is not produced with shift (사+t+T → ㄳㅆ) —
    **both are unguessable and both are just enumeration.** The cost was not in the
    Hangul rules but in repeating a claim instead of measuring what I was
    claiming about. Every failure in this file has the same shape: **a plausible-looking figure produced by a tool that cannot fail.**
14. **Re-derived the composition unit 11 times.** The same kind of thing. I
    spent a long time on the problem of turning Hangul words back into
    keystrokes without reading the header of `hunmin_ic_process` ("case encodes shift, 0x08 is backspace").

# 2. What I read without measuring (things that were facts straight from reading)

- **kime has no dictionary.** `grep -rniE 'dictionary|guess'` over `src/engine/`
  of kime 3.2.0 comes back empty. In this session this is the only claim
  about kime that has been measured.
- **fcitx5-hangul 5.1.9 has no Hangul/Latin mode at all**
  (no `latin|영어|ascii` in `src/hunminadapter.cpp`, `src/hunminadapter.h`; 0 Hangul/Latin
  options in `HangulConfig` besides keyboard/hanjaMode/wordCommit/autoReorder).
  The toggle is the business of the fcitx5 core. **Absence is not a judgement that this feature is unnecessary.**
- **namu.wiki is rejected.** CC BY-**NC**-SA 2.0 KR: "This work may not be
  used for commercial purposes." Distributing a deb (PPLAN.md P4 → PPA) is commercial use.
- **The SA is not a blocker.** `debian/copyright` is copyleft as
  `LGPL-2.1-or-later` and is on CC's list of compatible licences.

## The structure these have

- **kime's buffer structure** — `press_key(key, commit_buf: &mut String)`
  (`core/src/lib.rs:441`, the branch point via `InputCategory` at `:468`).
  This is the shape of the adapter, and the design did not invent it.
- **fcitx5-hangul's composition structure** — `LookupMethod`(`hunminadapter.cpp:181-231`)
  collects hanja across a composition and decides at completion. It is the same
  structure as kime's `commit_buf`, so there is **precedent twice**.
- **kime's hangul/latin selection** — `latin.preferred_direct: true` hands Latin
  keys to the OS. The grounds for not implementing QWERTY/DVORAK conversion.

# 3. What I got wrong while writing the requirement

15. **I argued it was unnecessary.** I wrote that no implementation does
    automatic Hangul/Latin switching, and that read like being against the
    feature. The user corrected me straight away: the absence in open source is a
    **capability gap**, and the request is to implement it with current capabilities. **Compare only on efficiency. Do not re-argue the requirement.**
16. **I laid down the premise "while composing" ahead of the requirement.** I
    defined the composition buffer of §ReqMode4 as "preedit text that is not yet
    finalized" and tried to fit the user's request into it. User correction:
    the composition buffer is the **entire span between whitespace/symbols**,
    not a syllable. That is, **the condition "only changes the text while composing" was itself a wrong constraint on this
    requirement.** If you fix the constraint first and fit the requirement to it, the requirement changes quietly.
17. **I widened the scope of a request without measuring.** The user said "when
    automatic conversion is **off**" and I promoted that case into a constraint
    on the on case, and used it to declare the options I had presented
    earlier "invalidated". User correction: that case only talked about the behavior when off. **Do not widen the scope of a quoted requirement yourself.**
18. **I misread what the number keys mean.** Seeing that `123` in
    `sin3-p2` commits immediately, I concluded "numeric input is not a
    problem". What I did not check was the **finalization tier path** — the number keys of
    `sin3-p2` are composed into Hangul jamo and are resolved at tier 101/102/103
    as `1` → `Ⅰ` / `₁` / `¹`. That is, **the digit run was already part of the
    composition**, and the requirement the user pointed at was exactly right. *There are times when a simple observation skips over a conditional branch.*
19. **I generalized an example into a rule.** The user said "he clearly typed
    it in Hangul but it changes to English" as **an example in one direction**,
    and I generalized it into a rule — "only this direction is allowed" — and
    put an asymmetry into ReqMode7. That (a) went beyond the scope the user described,
    and (b) collided head-on with ReqMode8's symmetry rule. Correction: the rule is
    **when the judgement diverges, depend on the current mode**, and the error is
    **the same weight in both directions.** A more important correction — the user
    themself proposed the direction of improvement: "since the user may
    deliberately type awkward words, if you can reduce having to turn this
    feature off and on manually, that is a better direction." That is, **reduce the number of manual interventions instead of regulating the direction of errors.** *When the user states a rule, read the example as an example, not as the scope of the rule.*
20. **I copied the user's proposition into the spec without verifying it.**
    The user said "even when a symbol appears no more Hangul is made, so
    English word compositions are not made either", and I **quoted that
    sentence as fact** and ended with "as the user explicitly stated." Once
    measured, **the proposition is false** — with `rk,rmf` it composes again
    after the comma, and `well-known` does not break at the hyphen. *If you
    quote on the assumption that what the user said is true, an unverified
    proposition hardens into a requirement and other people design on top of it.* The conclusion (a symbol is a separator) was right and the grounds were wrong, and I wrote both into the spec.
21. **I claimed absence without investigating.** I wrote in a commit message
    "this repository has no tools/ test target". **It was false.** Six Python
    scripts in `tools/` are registered with ctest — `data-selfcheck`,
    `schema-contract`, `frontend-invariants`, `frontend-mutations`,
    `trace-optout`, `keymap-fixture` (CMakeLists.txt:73-167) — and the
    mutation self-test pattern (`tools/frontend-mutations.py`, "a guard nobody
    has ever tried is only an assumption") was **already in that very repository.**
    *Writing "there is none" without checking that it does not exist is the same
    kind of thing as not verifying what the user said (entry 20).* Checking took
    2 minutes; the fact was a 1-minute fact. The real problem is not that, but that
    the fact **hides the gap** — it is not "there is no precedent" but the fact
    that it is "not registered yet", so the work that actually has to be done (ctest registration) disappeared from the document.
22. **I failed to distinguish a passing check from a valid check.** I thought
    that planting a mutation in selfcheck's truncation check and confirming the
    pass would be evidence that "the check can fail". But the mutation I planted
    was not itself a defect. `cur.append(
    line[:60])` concatenates the first 60 characters of each line, so it **still
    reads the whole page** — it passed with hangul 282,550 form, longest
    89,234. The real defect was a single-line reader that does not itself do
    `cur.append`, and you have to plant that for hangul 5,054·longest 1,976 to fail.
    *A check passing and what that check checks are separate things.* At the same
    time I re-picked the statistical threshold three times (different form/page →
    tokens/page → longest body length) — the first two only revealed themselves to be non-discriminating after measuring the full corpus. (docs/MODES-MEASUREMENT.md §5)

# 4. What goes into this list

Each entry should have the form: **what I got wrong** + **why it did not show
up.** And it separates "what I can say is wrong" from "what I cannot say
yet". The figures and the requirements live in other documents
(`docs/MODES-MEASUREMENT.md`, `docs/SPEC-MODES.md`); here I write only the
**failures of method.**

Focus on **the points the next attempt (whether a better model or a fresh
context) must not arrive at again.** Numbers can be re-measured, but **the way
you fabricate numbers** is easy to arrive at again.
